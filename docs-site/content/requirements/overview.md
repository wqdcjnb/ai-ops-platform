# 电商运营 AI API 统一管理平台需求文档

| --- | --- |
| 文档状态 | 需求评审稿 |
| 编制日期 | 2026 年 9 月 15 日 |

目标是让运营人员按职责安全使用合适的 AI 能力，同时让管理者清楚掌握用量 成本 风险和产出。

## 一 文档目的与结论

本项目拟建设统一的 AI API 管理平台，为多个电商运营岗位提供按用途分配的模型能力、独立访问凭证、可执行的额度策略和完整的流量监控。平台应将人员、业务用途、模型供应商和成本规则解耦，避免员工直接共享账号或上游密钥。

一期应优先完成四件事：统一入口、按人和用途发放 Key、额度与并发控制、可追溯的用量看板。上游模型应优先使用官方 API、合规第三方 API 或公司自建模型；个人订阅 OAuth 转换不作为生产依赖。

## 二 背景与业务问题

电商运营工作覆盖商品上新、标题与卖点生成、详情页优化、广告投放、客服回复、评价分析、竞品研究和数据复盘等场景。不同任务需要的模型能力、响应速度和成本不同，直接给所有人同一种模型或共享同一密钥，会造成成本失控、权限混乱和问题难以追溯。

| 当前问题 | 业务影响 | 目标状态 |
| --- | --- | --- |
| 账号或密钥共享 | 无法识别责任人，离职和泄露处置困难 | 每人独立身份和 Key，可随时禁用 |
| 模型使用无区分 | 简单任务也调用昂贵模型 | 按用途路由到不同模型等级 |
| 缺少额度控制 | 少数用户或异常任务耗尽预算 | 按人、部门、用途和周期设置硬限制 |
| 缺少实时监控 | 月底才发现成本异常 | 分钟级观察流量、Token、费用和错误 |
| 供应商耦合 | 切换模型需要逐台改客户端 | 网关统一模型别名和路由策略 |
| 数据边界不清 | 商品、客户和订单信息可能误发 | 敏感字段识别、脱敏和审计 |

## 三 项目目标与成功指标

### 3.1 业务目标

- 降低 AI 使用的平均任务成本，让高价模型集中处理高价值和高难度任务。

- 让运营人员获得稳定、易用的 AI 能力，不需要了解上游供应商和密钥细节。

- 把人员、用途、模型、额度和成本统一纳入管理，实现可追踪、可告警和可调整。

- 支持后续接入新的模型供应商、本地模型和业务系统，而不改变员工使用入口。

### 3.2 建议成功指标

| 指标 | 一期目标 | 统计口径 |
| --- | --- | --- |
| 人员覆盖率 | 试点团队 100% | 已领取有效 Key 且产生调用的试点人员占比 |
| 调用可归属率 | 不低于 99% | 可关联到用户、用途和客户端的请求占比 |
| 预算超限拦截率 | 100% | 达到硬额度后被正确阻止的请求占比 |
| 服务可用性 | 月度不低于 99.5% | 网关成功响应时间占比，不含上游故障 |
| 异常告警时效 | 5 分钟内 | 突增、错误率、余额不足到告警发出的时间 |
| 单位任务成本 | 试点后下降 20% | 同类任务平均模型成本与试点前对比 |

## 四 范围说明

### 4.1 一期范围

- 组织、部门、用户和角色管理。

- API Key 创建、停用、轮换、到期和用途绑定。

- 模型供应商与模型目录管理，支持模型别名。

- 按人员、岗位、用途、模型和周期配置额度及限流。

- 统一 OpenAI Responses 兼容入口，支持流式输出和工具调用。

- 请求量、Token、费用、延迟、错误率和剩余额度看板。

- 阈值告警、审计日志、数据导出和基础成本分摊。

### 4.2 暂不纳入一期

- 训练或微调自有大模型。

- 替代完整的电商 ERP、客服或广告投放系统。

- 自动执行高风险运营动作，例如自动调价、自动退款和自动充值。

- 依赖个人订阅账号共享或将个人订阅 OAuth 转换为生产 API。

## 五 用户角色与权限

| 角色 | 主要职责 | 核心权限 |
| --- | --- | --- |
| 平台管理员 | 维护组织、供应商、模型和全局策略 | 全局配置、密钥管理、审计和应急处置 |
| 部门负责人 | 分配团队预算并观察产出 | 查看本部门、调整下级额度、审批申请 |
| 运营人员 | 使用授权模型完成运营工作 | 查看个人 Key、用量、剩余额度和使用说明 |
| 财务人员 | 核对成本和供应商账单 | 只读查看费用、预算、分摊和导出数据 |
| 安全审计员 | 检查异常访问与数据风险 | 只读查看审计、告警和安全事件 |
| 系统集成账号 | 供自动化流程或业务系统调用 | 限定用途、模型、来源 IP 和有效期 |

## 六 典型业务用途与模型分配

平台不直接向员工暴露供应商模型名，而是提供稳定的业务模型别名。管理员可以在后台调整别名对应的实际模型、价格和降级策略。

| 业务用途 | 使用人员 | 模型等级建议 | 控制策略 |
| --- | --- | --- | --- |
| 标题与卖点生成 | 商品运营 | 低成本快速模型 | 高并发，限制单次输入和输出长度 |
| 详情页和活动文案 | 内容运营 | 均衡模型 | 按日额度，支持品牌词库和模板 |
| 多语言翻译与本地化 | 跨境运营 | 均衡或专业翻译模型 | 按语种路由，保留术语表 |
| 客服回复建议 | 客服与售后 | 低延迟模型 | 脱敏订单信息，禁止自动发送 |
| 评价聚类与情绪分析 | 用户运营 | 批量低成本模型 | 批处理队列，限制并发 |
| 竞品研究与策略分析 | 运营主管 | 高能力推理模型 | 较低并发，审批后提高额度 |
| 广告素材与投放复盘 | 广告运营 | 均衡和高能力组合 | 素材生成与分析分别计费 |
| 图片理解与素材检查 | 视觉与商品运营 | 视觉模型 | 限制图片大小、数量和保存期限 |

## 七 总体业务流程

1. 管理员接入合规的上游 API 或内部模型，并录入价格、可用区域、能力和健康检查规则。

1. 管理员创建业务用途和模型别名，配置主模型、备用模型、成本上限和数据策略。

1. 部门负责人添加人员，为每个人分配独立 Key、允许用途和周期额度。

1. 运营人员在 Codex 桌面端、内部工具或自动化流程中使用分配的 Key。

1. 网关完成身份验证、额度检查、内容策略检查和模型路由，然后转发请求。

1. 平台记录用量与结果状态，更新预算并在异常时告警。

1. 负责人通过看板分析人员、用途和模型成本，调整额度或路由策略。

## 八 系统架构建议

| 层级 | 主要组件 | 职责 |
| --- | --- | --- |
| 使用入口 | Codex 桌面端、浏览器工具、运营自动化 | 保存各自任务记录，携带个人 Key 和用途标识 |
| 统一网关 | 认证、限流、路由、协议适配 | 提供统一域名，隐藏上游密钥和供应商差异 |
| 治理服务 | 用户、Key、额度、审批、审计、告警 | 执行管理规则并形成可追踪记录 |
| 数据与监控 | SQLite（试点）、MySQL/PostgreSQL（正式）、可选缓存、指标、日志 | 保存配置、用量聚合、状态和审计数据 |
| 模型供应层 | 官方 API、第三方 API、本地模型 | 提供不同能力、成本和可用性的模型服务 |

建议将模型调用内容与运营数据分开治理。默认记录调用元数据，不长期保存完整提示词和模型输出；确需排障时采用短期、脱敏、受控留存。

| FR-17 | 自动降级 | 高价模型额度不足或故障时，可按策略切换到低成本备用模型。 | 应该 |

## 十 额度与流量控制规则

### 10.1 额度层级

- 全局预算：控制整个平台在一个结算周期内的最大可用成本。

- 部门预算：由业务负责人分配，部门内所有人员共享或独立核算。

- 个人预算：控制单个运营人员的周期消耗。

- 用途预算：防止批量翻译、图片或研究任务占用过多资源。

- Key 预算：用于临时项目、外包人员和系统集成。

### 10.2 判定顺序

请求进入后依次检查 Key 状态、来源限制、用途权限、模型权限、并发、速率、个人额度、部门额度和全局额度。任一硬限制不满足时立即拒绝，并返回可识别的错误码及剩余额度说明。

### 10.3 建议初始策略

| 对象 | 建议策略 | 原因 |
| --- | --- | --- |
| 普通运营人员 | 较高的低成本模型额度，较低的高能力模型额度 | 满足日常高频任务并控制推理成本 |
| 运营主管 | 增加高能力模型额度和最大上下文 | 支持复杂分析与策略制定 |
| 批处理任务 | 独立 Key、低优先级队列、严格并发 | 避免抢占交互请求资源 |
| 临时项目 | 设置到期时间和一次性预算 | 项目结束后自动收回权限 |
| 异常调用 | 连续错误或突增时自动降速或暂停 | 减少脚本循环和密钥泄露损失 |

## 十一 监控与报表

### 11.1 实时监控指标

| 类别 | 核心指标 |
| --- | --- |
| 流量 | 请求数、成功数、并发数、RPM、TPM、输入与输出 Token |
| 成本 | 实时估算费用、当日和当月累计、预算消耗率、剩余额度 |
| 性能 | 平均延迟、首字延迟、P95、P99、流式中断率 |
| 质量与稳定性 | 错误率、429、5xx、超时、重试、降级和供应商切换次数 |
| 人员与用途 | 活跃用户、Top 用户、用途分布、模型分布、单位任务成本 |
| 安全 | 无效 Key、异常 IP、短时突增、越权模型调用和敏感策略拦截 |

### 11.2 看板页面

- 总览：今日调用、今日费用、成功率、活跃人数、预算完成度和告警。

- 人员：个人趋势、模型分布、用途分布、错误和剩余额度。

- 部门：预算、消耗、人员排行和环比变化。

- 模型：调用量、成本、延迟、错误率和替代模型对比。

- 供应商：余额、健康状态、费率、限流和故障切换记录。

- 审计：配置变更、Key 生命周期和异常访问事件。

## 十二 安全与合规要求

| 编号 | 要求 |
| --- | --- |
| SEC-01 | 上游密钥、OAuth Token 和用户 Key 必须加密存储，界面只显示掩码。 |
| SEC-02 | 禁止在日志、错误信息、导出文件和监控标签中记录完整密钥。 |
| SEC-03 | 管理员启用多因素认证；高权限操作记录审计并支持二次确认。 |
| SEC-04 | 客户端到网关必须使用 HTTPS 或可信内网 VPN，禁止公网明文传输。 |
| SEC-05 | 支持 IP 白名单、Key 有效期、最小权限和定期轮换。 |
| SEC-06 | 默认不长期保存完整提示词和回答；日志留存周期可配置。 |
| SEC-07 | 订单号、手机号、地址和客户信息进入模型前应按策略脱敏。 |
| SEC-08 | 供应商接入需登记数据使用范围、区域、保留政策和合同状态。 |
| SEC-09 | 不将个人订阅账号共享或 OAuth 转换作为正式生产 API 来源。 |
| SEC-10 | 人员离职或岗位调整后，相关 Key 和权限应在约定时限内自动收回。 |

## 十三 非功能需求

| 类别 | 要求 |
| --- | --- |
| 可用性 | 一期月度可用性不低于 99.5%；关键组件具备自动恢复和健康检查。 |
| 性能 | 网关自身增加的非流式处理延迟 P95 不超过 200 毫秒，不含上游响应时间。 |
| 扩展性 | 首期支持 100 名用户、100 个并发请求和每日 10 万次请求，可水平扩展。 |
| 兼容性 | 优先支持 OpenAI Responses API、SSE 流式输出、工具调用和图片输入。 |
| 一致性 | 额度扣减在并发场景下不得出现明显超发；关键配置变更应在 60 秒内生效。 |
| 可维护性 | 供应商、模型、价格和路由策略通过配置管理，无需修改客户端。 |
| 可观测性 | 日志、指标和追踪具备统一请求 ID，可关联用户、用途和上游请求。 |
| 备份恢复 | 配置、用户、额度和审计数据每日备份；恢复目标时间不超过 4 小时。 |

## 十六 异常与降级策略

| 异常场景 | 系统行为 |
| --- | --- |
| 上游超时或 5xx | 按策略重试；仍失败则切换同等级备用模型并记录降级。 |
| 上游 429 | 遵循重试时间，降低并发；必要时切换有剩余额度的供应商。 |
| 个人额度耗尽 | 拒绝高成本模型；允许时切换到低成本模型或发起临时额度申请。 |
| 供应商余额不足 | 提前告警，停止新流量进入该供应商并切换备用路由。 |
| Key 疑似泄露 | 自动暂停 Key、通知管理员并保留相关审计证据。 |
| 统计服务异常 | 默认执行保守额度策略；不得因统计失败无限放行。 |
| 价格信息缺失 | 标记成本未知并限制模型进入生产路由。 |

## 十七 验收标准

| 编号 | 验收条件 |
| --- | --- |
| AC-01 | 管理员可创建用户并在 2 分钟内为其生成带用途和到期时间的 Key。 |
| AC-02 | 两个不同用户使用各自 Key 调用时，系统能分别统计请求、Token 和费用。 |
| AC-03 | 用户达到小时、日或月硬额度后，新请求被正确拒绝且不影响其他用户。 |
| AC-04 | 管理员修改业务模型别名后，客户端无需更改配置即可使用新路由。 |
| AC-05 | 主模型不可用时，符合策略的请求自动切换备用模型并留下记录。 |
| AC-06 | 看板可按人员、部门、用途、模型和时间筛选，统计与调用日志抽样一致。 |
| AC-07 | 流量突增、错误率超阈值和预算达到 80% 时能在 5 分钟内产生告警。 |
| AC-08 | 禁用或轮换 Key 后，旧 Key 在 60 秒内失效。 |
| AC-09 | 导出文件不包含完整密钥、OAuth Token 或未脱敏客户敏感信息。 |
| AC-10 | Codex 桌面端通过自定义 Provider 完成流式对话、工具调用及任务恢复测试。 |

## 十八 实施阶段

| 阶段 | 建议周期 | 交付内容 |
| --- | --- | --- |
| 准备阶段 | 1 周 | 确定用户清单、用途、预算、供应商和数据等级；完成架构评审。 |
| 一期 MVP | 2 至 4 周 | 用户、Key、模型路由、额度、限流、基础看板、日志和告警。 |
| 试点阶段 | 2 周 | 选择 5 至 10 名运营人员，验证成本、稳定性、任务效果和流程。 |
| 二期优化 | 2 至 4 周 | 审批、成本分摊、模板库、自动降级、账单核对和细化报表。 |
| 推广阶段 | 持续 | 扩大人员和用途，按数据调整模型组合、额度与培训材料。 |

## 十九 风险与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 模型费用波动 | 预算预测偏差 | 维护版本化价格表，设置全局硬上限和余额告警 |
| 供应商服务中断 | 运营任务无法完成 | 配置健康检查、备用供应商和人工降级流程 |
| Key 泄露 | 异常消耗和数据风险 | 独立 Key、短有效期、IP 限制、异常检测和快速吊销 |
| 敏感数据外发 | 客户隐私和合规风险 | 数据分级、脱敏、用途限制和供应商审查 |
| 统计不准确 | 额度和成本分摊错误 | 原始计量、幂等扣费、账单核对和差异报告 |
| 模型效果不稳定 | 运营产出质量下降 | 模板、评测集、人工复核和分用途模型评估 |
| 个人订阅代理 | 账号限制或服务中断 | 生产环境使用官方 API、合规第三方 API或自建模型 |

## 二十 待确认事项

1. 首期使用人数、部门结构以及未来十二个月预计增长。

1. 每个岗位的高频任务、平均调用次数和可接受响应时间。

1. 月度总预算，以及部门和个人是否需要硬性等额分配。

1. 计划接入的官方 API、第三方 API和本地模型清单。

1. 是否需要公网访问，还是仅在公司内网或 VPN 中使用。

1. 允许发送到外部模型的数据范围，以及订单、客户和商品数据的脱敏规则。

1. 告警通知渠道、审批人和异常处置值班机制。

1. 调用明细和完整内容的留存周期，以及财务和审计导出格式。

## 二十一 建议的立项决策

建议批准一期 MVP，以 5 至 10 名电商运营人员进行两周试点。试点只接入一到两个稳定且合规的模型来源，为每位人员发放独立 Key，并强制配置个人、部门和全局三层额度。上线前完成数据分级、Key 管理和异常停用演练；试点结束后根据单位任务成本、质量、稳定性和人员采用率决定是否扩大。
