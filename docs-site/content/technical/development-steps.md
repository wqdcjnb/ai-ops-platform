## 1. 开发结论

项目采用“先验证链路，再建设管理层，最后正式上线”的顺序：

```text
阶段 A：本机链路验证
  ↓ 协议、流式、工具调用和路由隔离通过
阶段 B：5–10 人团队试点
  ↓ 独立 Key、用量归属、软额度和连续运行通过
阶段 C：统一运营控制台
  ↓ 只读聚合稳定后开放受控写操作和硬额度
阶段 D：正式内网上线
  ↓ 安全、恢复、性能和运营验收通过
阶段 E：精细运营与持续优化
```

以下边界在整个开发过程中保持不变：

- 不自行重写模型转发内核。New API 负责员工身份、内部 Key、模型权限、渠道和用量；CPA 负责 Pro OAuth 隔离实验和协议适配。
- 正式业务只接公司拥有或明确授权的 API；个人 Pro OAuth 不作为生产容量，也不能成为正式模型的隐式备用渠道。
- 浏览器只访问平台 BFF，不直接访问 New API/CPA 管理接口，不保存任何管理密钥。
- 默认只记录请求元数据，不长期保存完整提示词、回答、文件正文、源代码或客户敏感数据。
- 本机验证和低并发试点使用 SQLite；进入长期在线、多实例或高并发阶段后，再迁移 MySQL/PostgreSQL。
- 试点阶段的 80%/100% 为软额度提示；正式运营阶段的硬额度必须在并发一致性和结算测试通过后启用。

## 4. 阶段 0：冻结范围与业务规则

### 目标

把会改变数据模型、计费结果或部署方式的事项先确定，避免开发中途重做。

### 开发前必须确认

1. 确定 5–10 名试点人员、部门、岗位、负责人和离职/停用流程。
2. 确定正式上游供应商、实验上游账号、业务模型目录和测试预算。
3. 确定预算单位：Token、平台点数、估算金额或组合；明确官方 API 实际账单与 Pro 订阅估算值分开展示。
4. 确定日/月周期、重置时区、取消请求如何结算、失败和重试是否计费。
5. 确定一期用途目录，至少包括文案、客服、翻译、分析和自动化。
6. 确定客户数据分级、允许发送到外部模型的字段及脱敏规则。
7. 确定告警接收人；试点先在平台记录事件，企业微信/钉钉推送可留到二期。

### 交付物

- 《试点人员与角色清单》
- 《模型、渠道与业务别名映射表》
- 《预算和计费口径表》
- 《数据分级与日志留存规则》
- 更新后的决策记录和待办负责人

### 退出条件

所有待确认项都有明确结论，或被书面标记为“不阻断本机验证、阻断团队试点/正式上线”。

## 5. 阶段 A：完成本机最小链路验证

### A1. 固定环境基线

1. 记录 Codex Desktop、WorkBuddy、New API、CPA、Node.js 和数据库版本。
2. 固定 New API 与 CPA 版本或镜像摘要，禁止使用不可回滚的浮动版本。
3. New API 使用持久化 SQLite；测试阶段不引入 Redis、MySQL 或 PostgreSQL。
4. 将运行配置、数据库、日志、OAuth 文件和密钥排除在 Git 之外。
5. 为正式渠道和 CPA 实验渠道建立完全不同的分组与模型别名。

### A2. 建立最小请求链路

1. 在 New API 创建一个管理员测试用户和低额度内部 Key。
2. 接入一个合规正式 API 渠道，配置业务模型别名，不向客户端暴露真实供应商模型名。
3. 如需验证 CPA，使用独立实验账号，只开放 `ecommerce-pro-lab`，不配置到正式模型的回退链路。
4. 分别配置 Codex Desktop 和 WorkBuddy 指向 New API，记录实际请求接口与 Header 行为。
5. 为每个请求生成或透传统一请求 ID，确认 New API 与 CPA 日志能否关联同一次调用。

### A3. 按固定顺序执行兼容性测试

1. 普通非流式请求。
2. SSE 流式输出和首 Token 延迟。
3. Function Calling/工具调用及结果回传。
4. MCP、图片等扩展能力；未配置支持渠道时标记“不适用”，不得假定支持。
5. 长任务、客户端取消、网络中断和超时。
6. 客户端重启、Provider 切换和历史记录恢复。
7. 主渠道停止、CPA 停止、账号失效和 429/5xx 行为。

### 阶段交付物

- 每个客户端一份兼容性测试记录
- 请求 ID 关联结论和已确认的统计字段
- 正式/实验模型路由矩阵
- 不兼容项、绕行方案和是否阻断试点的结论

### 退出条件

- 正式渠道不依赖 CPA，CPA 停止不影响正式模型。
- 正式渠道故障时不会自动消耗 Pro OAuth。
- 流式、工具调用、取消和长任务的实际行为已有可复现记录。
- 客户端只持有内部 Key，不持有上游密钥或管理密钥。

## 6. 阶段 B：搭建团队试点能力

### B1. 建立试点组织和 Key

1. 在 New API 创建试点用户，建立“人员—部门—岗位—负责人”的外部台账；原生字段不足时先用稳定映射，不立即修改转发内核。
2. 每名员工按模型分别签发独立 Key，填写用途、一个绑定模型、有效期和设备备注；同一员工需要多个模型时创建多个 Key。
3. Key 明文只在创建时显示一次；列表、日志、导出和截图只显示掩码。
4. 验证停用、轮换和离职回收流程，旧 Key 必须在 60 秒内失效。
5. 默认拒绝未授权模型；普通用户不能提交任意上游地址或选择渠道。

### B2. 配置软额度和用量归属

1. 为试点人员设置相同的初始月度目标，特殊岗位差异需记录审批原因。
2. 先展示 80%“接近目标”和 100%“已达目标”，试点阶段不自动中断请求。
3. 按人员、Key、模型别名、渠道和日期核对请求数、输入/输出 Token、错误和延迟。
4. 官方 API 的实际账单单独核对；CPA/订阅流量只能显示估算消耗，不得标为实际成本。
5. 对取消、失败、重试和流式中断建立统一统计规则。

### B3. 建立基础运营保障

1. 每日备份 New API 整个数据目录；CPA 的配置和认证文件分开加密备份。
2. 记录预算 80%/100%、认证刷新失败、可用账号不足、错误率和流量突增事件。
3. 制定 Key 泄露、账号失效、异常费用和渠道故障的人工处置流程。
4. 为试点人员提供不含密钥的客户端接入说明和常见错误说明。

### 退出条件

- 两名测试用户的数据完全隔离，未授权模型在到达上游前被拒绝。
- 用量抽样与调用记录一致，正式账单与估算数据有明确区分。
- 备份文件可在隔离环境恢复，恢复后用户、Key、渠道和用量数量一致。
- 满足条件后开放 5–10 人试点，连续运行两周。

## 7. 阶段 B 验证：连续两周试点

试点期间只修复阻断问题和记录真实使用，不在未验证数据基础上扩展大量功能。

### 每日观察

- 请求量、Token、成功率、429/5xx、平均/P95 延迟和流式中断率。
- 活跃人员、个人用量、模型分布、正式/实验渠道分布。
- Key 异常 IP、连续鉴权失败、流量突增和账号刷新失败。
- New API 数据库增长、SQLite 锁等待、日志和磁盘使用量。

### 每周复盘

- 按业务用途抽样产出质量与单位任务成本。
- 核对平台估算与官方供应商账单差异。
- 复盘人工运维耗时，确定统一控制台必须优先解决的操作。
- 将接口字段、分页、错误码和版本差异整理成 BFF 适配清单。

### 退出条件

- 调用可归属率不低于 99%。
- 连续两周没有跨用户数据泄露、正式/实验路由串用或无法解释的费用异常。
- 已确定统一控制台 MVP 的真实数据源和接口缺口。
- 严重兼容性问题都有修复方案；无法修复的问题已明确缩减范围。

## 8. 阶段 C：开发统一运营控制台

阶段 C 才进入 `apps/server` 和 `apps/web` 的业务实现。先完成只读聚合，再开放影响 Key、预算和路由的写操作。

### C1. 固定领域模型与 BFF 契约

先定义平台自己的稳定对象，不让页面直接依赖上游接口字段：

| 对象 | 必要字段 |
| --- | --- |
| 人员 | ID、姓名、部门、岗位、状态、负责人、最后使用时间；业务用途归属于 Key |
| Key | ID、人员、用途、绑定模型（单 Key 单模型）、状态、到期时间、最近使用时间、掩码 |
| 模型路由 | 业务别名、渠道类型、实际模型、正式/实验标记、健康状态 |
| 用量 | 请求 ID、人员、Key、用途、模型、渠道、Token、延迟、状态、估算费用 |
| 预算 | 作用对象、周期、单位、上限、已用、预留、重置时间、软/硬模式 |
| 告警 | 规则、对象、级别、触发值、状态、确认人、处理时间 |
| 审计 | 操作人、动作、对象、变更摘要、来源 IP、时间、结果 |

BFF 第一批接口建议按以下资源拆分：

```text
GET  /api/overview
GET  /api/people
GET  /api/people/:id
GET  /api/keys
GET  /api/routes
PATCH /api/routes/:id  # 仅本地 SQLite 的降级与重试策略覆盖
GET  /api/usage
GET  /api/upstreams
GET  /api/alerts
GET  /api/audit-events
```

所有第三方返回值先经 Zod 校验和适配，再返回统一错误结构、分页结构和请求 ID。接口契约确定后生成模拟数据，前后端可并行开发。

### C2. 实现 Fastify BFF 只读层

1. 建立配置加载、启动校验、结构化日志和全链路请求 ID。
2. 在服务端接入 New API 与 CPA 管理接口，管理凭据只从受保护配置读取。
3. 实现上游超时、错误分类、有限重试和熔断；禁止把上游完整错误正文返回浏览器。
4. 对人员、Key、用量、模型和账号状态做字段适配、分页和短时缓存。
5. 加入来源限制、Helmet、安全 CORS 和管理接口限流。
6. 编写适配器单元测试、敏感字段快照测试和上游异常测试。

### C3. 实现 Vue 只读页面

按“先高频运营、后低频配置”的顺序开发：

1. 应用外壳、路由、权限守卫、错误页和全局状态。
2. 运营总览：今日请求、Token、软目标、成功率、P95、异常队列。
3. 人员与 Key：筛选、人员详情、Key 掩码、到期和用量状态。
4. 用量与日志：日期、人员、部门、模型、渠道、状态和请求 ID 筛选。
5. 模型与渠道：业务别名、正式/实验标签、实际路由和健康状态。
6. 上游账号、告警、审计和设置页面。

页面采用已确定的 Tabler 高密度工具风；状态不能只依赖颜色，金额、Token、百分比和延迟右对齐。浏览器 Network、源代码、localStorage 和构建产物中不得出现管理密钥。

### C4. 开放受控写操作

只读版本稳定后，按风险从低到高依次开放：

1. 确认/关闭告警。
2. 调整人员软目标。
3. 创建、停用和轮换 Key。
4. 修改人员状态；模型绑定只在 Key 管理中维护。
5. 修改业务模型别名和路由。
6. 配置硬额度和自动降级。

每个写操作必须具备：服务端权限校验、请求校验、幂等保护、二次确认、变更前后摘要、审计事件、明确失败提示和回滚方式。前端隐藏按钮不能替代服务端授权。

### C5. 实现硬额度与并发控制

硬额度不得直接沿用试点软目标。实现时必须：

1. 按 Key 状态、来源、用途、模型、并发/RPM/TPM、人员、部门和全局顺序判定。
2. 请求开始时预留最大可用额度，请求结束后按实际用量结算并释放差额。
3. 为重复回调、上游重试、取消和统计补录设置幂等键。
4. 统计服务异常时采用保守策略，不能无限放行。
5. 返回稳定错误码、命中层级、重置时间和可用替代模型，不返回内部配置。
6. 通过并发压测证明没有明显超发，再把硬额度用于正式用户。

### 阶段交付物

- OpenAPI/接口契约和领域模型说明
- Fastify BFF、Vue 控制台和环境配置模板
- 单元、组件、集成和 Playwright 测试
- 管理操作审计、错误码和回滚说明
- 三个优先高保真页面及完整 MVP 页面

### 退出条件

- 管理员日常查看人员、Key、用量、渠道和异常无需在多个后台之间反复切换。
- 浏览器不直连上游管理接口，不持有 New API/CPA 管理密钥。
- 两个角色的数据范围和所有写操作都通过服务端权限测试。
- 创建、停用、轮换 Key、调整预算及人员状态均可追溯并可验证结果；每个 Key 绑定一个全局业务模型，本地模拟写操作不会冒充真实上游状态。
- 硬额度并发、取消、重试和故障测试通过后，才允许开启阻断模式。

## 9. 阶段 D：正式内网部署与上线

### D1. 部署拓扑

1. 从个人电脑迁移到长期在线的公司内网服务器。
2. 使用 Caddy 建立独立调用域名与管理域名；调用域名只开放必要模型接口。
3. 仅开放 HTTPS，证书来自可信 CA；管理域名接入 VPN、零信任或严格来源限制。
4. New API、CPA、数据库、缓存和监控端口不直接暴露公网。
5. 开发、测试和生产使用不同上游项目、Key、数据库和备份。

### D2. 数据库与状态迁移

出现长期在线、多实例、并发写入锁等待或集中备份需求时迁移到 MySQL/PostgreSQL：

1. 在 SQLite 副本上完成导出并校验备份。
2. 导入目标数据库，核对用户数、Key 数、渠道数、用量汇总和审计数量。
3. 在隔离环境验证登录、查询、写操作和额度结算。
4. 演练回滚，记录允许停机时间和数据增量处理方式。
5. 正式切换后保留只读备份，不立即销毁原数据。

### D3. 上线验收

- 功能：人员、Key 绑定模型、路由、用量、告警、审计和导出。
- 兼容：Codex Desktop、WorkBuddy、流式、工具、MCP、长任务、取消和恢复。
- 安全：伪造代理头、未授权模型、超大请求、日志密钥标记和管理面隔离。
- 性能：网关自身非流式附加延迟 P95 不超过 200 ms；验证 100 并发目标或批准后的实际容量目标。
- 可用性：健康检查、组件重启、上游 429/5xx、主渠道故障和自动恢复。
- 恢复：从加密备份恢复到隔离环境，恢复目标时间不超过 4 小时。

### 上线阻断项

以下任一问题存在时不得上线：

- 客户端或浏览器可获得上游 Key、OAuth Token 或管理密钥。
- 普通调用域名能够访问管理 API。
- 日志、导出、监控标签或前端资源包含完整凭据或未脱敏客户数据。
- Key 撤销超过 60 秒仍有效，或不同员工可访问对方数据。
- 正式业务依赖个人订阅 OAuth，或正式模型可隐式回退到 CPA 实验渠道。
- 硬额度在并发下明显超发，统计故障时无限放行。
- 数据库/备份未加密、恢复未演练，或部署版本无法回滚。

## 10. 阶段 E：二期精细运营

正式版本稳定后再按业务收益排序开发：

1. 临时额度申请、负责人审批、生效和自动到期。
2. 企业微信/钉钉通知、告警去重、静默和升级策略。
3. 部门成本分摊、月报、供应商账单核对和差异报告。
4. 提示词模板、品牌术语、禁止词和版本管理。
5. 敏感信息自动识别与脱敏策略。
6. 分用途模型质量评测、A/B 对比和单位任务成本优化。
7. 企业单点登录、多机高可用、共享缓存和灾备。

二期每项功能仍遵循“小范围验证—数据核对—扩大范围”的发布方式。

## 11. 测试与质量门禁

| 层级 | 最小覆盖 | 进入下一阶段的要求 |
| --- | --- | --- |
| 静态检查 | TypeScript、Vue TSC、文档链接和敏感词扫描 | 0 个阻断错误 |
| 单元测试 | 数据适配、金额/Token 计算、权限、错误映射、脱敏 | 核心规则和边界场景通过 |
| 集成测试 | BFF ↔ New API/CPA、超时、分页、版本字段变化 | 不泄漏凭据，错误可定位 |
| 端到端测试 | 登录、添加人员、CSV 批量导入、创建 Key、预算、告警处置和审计回溯 | `apps/web/e2e/critical-flows.spec.ts` 的 6 条关键流程通过；接入真实数据后再补充跨环境账号和浏览器兼容矩阵 |
| 并发测试 | 额度预留、重复请求、取消、重试、统计失败 | 无明显超发或重复扣减 |
| 安全测试 | 越权、SSRF、代理头、超大请求、日志密钥标记 | 所有上线阻断项为零 |
| 恢复测试 | 数据库、New API 数据、CPA 配置/认证备份 | 可在 4 小时内恢复且数量核对一致 |

每个缺陷应关联需求编号、测试证据、影响范围和修复版本。聊天成功、页面能打开或依赖可安装都不能单独视为业务验收通过。

## 12. 推荐任务拆分顺序

```text
EPIC-01 规则冻结与试点准备
EPIC-02 New API 正式渠道最小链路
EPIC-03 CPA 隔离实验链路
EPIC-04 客户端兼容性与故障测试
EPIC-05 试点人员、Key、模型别名与软额度
EPIC-06 用量核对、备份恢复与两周试点
EPIC-07 平台领域模型和 BFF 接口契约
EPIC-08 BFF 只读聚合与安全边界
EPIC-09 Vue 运营控制台只读 MVP
EPIC-10 Key、人员、预算和路由写操作
EPIC-11 硬额度、限流、告警与审计
EPIC-12 正式部署、迁移、安全与性能验收
EPIC-13 二期审批、报表、模板和高可用
```

依赖关系上，`EPIC-02～04` 必须先于业务控制台；`EPIC-06` 的真实接口和数据结论是 `EPIC-07～09` 的输入；`EPIC-10` 必须晚于只读聚合稳定；`EPIC-11` 必须完成并发一致性测试后才能进入 `EPIC-12`。

## 13. 完成定义

一个开发任务只有同时满足以下条件才算完成：

- 需求、权限边界、异常行为和验收条件明确。
- 代码、配置模板和必要文档已更新，不包含真实凭据。
- 类型检查、相关单元/集成/端到端测试通过。
- 日志、错误和导出完成敏感信息检查。
- 对外部系统的假设已用当前版本实际验证。
- 有部署、回滚和运营说明；高风险变更有审计证据。
- 项目待办、决策记录和更新记录与实际状态一致。
