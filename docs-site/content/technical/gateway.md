# 网关路由与低延迟

## 1. 已交付的路由原则

员工、Codex 和 WorkBuddy 对外只看见一个模型：`ai-ops`（显示名为“AI OPS”）。网关不会把中转站名、原始模型名或中转站凭据暴露给客户端。

每次请求的目标是同时满足两件事：尽快选择一个健康中转站，以及绝不因为“找最快”而重复执行用户的真实请求。尤其是图片、视频和音频请求，重复提交可能产生两份结果和两次费用，因此不能对真实生成请求做竞速。

~~~mermaid
sequenceDiagram
  participant C as 员工客户端
  participant G as 统一模型网关
  participant A as 中转站 A
  participant B as 中转站 B
  participant D as 中转站 C

  C->>G: ai-ops + 平台 Key
  G->>A: /models 健康探测
  G->>B: /models 健康探测
  G->>D: /models 健康探测
  B-->>G: 最先成功
  G-xA: 取消未完成探测
  G-xD: 取消未完成探测
  G->>B: 一次真实文本 / 图片 / 视频 / 音频请求
  B-->>G: 结果或流
  G-->>C: 响应，model 仍为 ai-ops
~~~

## 2. 多站并发竞速（当前实现）

当中转站健康信息过期时，网关会从可用中转站中取一个**有上限的并发样本**，同时发起轻量的 `GET /models` 探测：

- 默认同时探测 3 个站点，可用环境变量 `AI_OPS_RELAY_PROBE_FANOUT` 配置为 2 到 8。
- 所有探测在同一时刻启动；第一个成功返回的站点获胜。
- 获胜后立即取消其他未完成探测，不等待最慢站点。
- 健康结果在内存中短暂缓存（当前为 15 秒）；缓存有效时不会再次探测。
- 当站点数超过并发上限时，抽样起点会轮转，避免按名称排在前面的站点长期垄断请求。
- 手工“健康检查”、获取模型列表和保存/同步时使用相同的轻量模型目录请求；它们不会触发任何生成任务。只有管理员显式点击“测试已选模型”时，系统才会向文本候选发送最小文本探测：先试 Chat Completions，再在前者不兼容时试 Responses。目录元数据或保守模型名识别出的图片、视频、语音模型只标记为“目录已确认”，不自动创建可能计费的媒体任务。

这解决的是“多个站点怎么更快找最快”的问题：探测是并发的、可取消的、有上限的；真实调用只发生在选定站点上。

## 3. 真实请求、回退与并发安全

竞速结束后，网关只向获胜站点发送**一次**真实请求。请求成功后记录该站点的近期延迟；若真实调用在尚未产出结果前发生可重试故障，网关才按候选顺序尝试下一个站点。

| 请求类型 | 选择最快 | 真实调用 | 可回退的时点 |
| --- | --- | --- | --- |
| 文本 / Chat Completions | 并发 `/models` 探测 | 仅一个站点 | 首个可见流式片段之前 |
| Responses | 并发 `/models` 探测 | 仅一个站点 | 首个事件之前 |
| 图片生成 | 并发 `/models` 探测 | 仅一个站点 | 上游尚未确认执行且错误可重试时 |
| 视频请求 | 并发 `/models` 探测 | 仅一个站点 | 上游尚未确认执行且错误可重试时 |
| 语音生成 | 并发 `/models` 探测 | 仅一个站点 | 上游尚未确认执行且错误可重试时 |

不会做以下事情：

- 不会同时向多个中转站发送同一个提示词来比“谁先生成”。
- 不会在流已经输出内容后从头重试，避免重复或断裂的对话。
- 不会在网关热路径串行检查所有中转站。
- 不会为了取模型列表阻塞员工调用；公开的 `/v1/models` 始终只返回 `ai-ops`。

当前可安全回退的错误包括上游连接失败、超时、限流和可识别的服务端可用性错误。认证失败、参数错误和内容策略拒绝不会切换站点重试。

## 4. 多模态统一入口

同一个员工 Key、同一个 `ai-ops` 和同一套中转站竞速逻辑用于下列 JSON 请求。网关在服务端把已选模型归入文本、图片、视频或语音候选组；每个端点只从匹配的组中选最快健康站点，绝不把图片/视频/语音模型发送到文本聊天接口，反之亦然。该归类优先采用上游目录元数据，缺失时仅使用保守模型名提示，且不会在员工目录中显示为未经验证的“能力”。

| 路径 | 用途 | 当前网关行为 |
| --- | --- | --- |
| `/v1/chat/completions` | 对话、代码、流式输出 | 兼容 OpenAI Chat Completions 并透传流 |
| `/v1/responses` | Responses 风格文本与代码 | 使用上游兼容的 Responses 协议 |
| `/v1/images/generations` | 图片生成 | 选择胜出站点后原样转发 JSON 响应 |
| `/v1/videos` | 视频生成或上游视频任务 | 选择胜出站点后保留上游任务/结果语义 |
| `/v1/audio/speech` | 语音合成 | 选择胜出站点后原样转发 JSON 响应 |

媒体端点的 `model` 未填写时，网关会默认补为 `ai-ops`；填写其他模型会被拒绝。当前阶段只支持这些 JSON 端点，不把图片编辑的 multipart 上传、音频转写、大文件资产托管或平台自建视频 job 状态机伪装成已经可用的能力。那些能力可在后续独立媒体作业服务中增加。

## 5. 健康、隔离和容量演进

当前路由器根据最近探测延迟和失败次数排序，并在 15 秒内复用健康结论。中转站被管理员停用、没有有效凭据或没有同步到模型时，不会进入候选集。

下一阶段的容量演进应保持这一不重复执行原则：

- 将内存健康快照扩展为共享缓存，使多网关实例使用一致的健康和熔断状态。
- 以“中转站 + 上游模型 + 模态”记录 TTFT、队列时间、成功率、429 和并发数。
- 对每个中转站设置独立连接池、在途上限与熔断冷却，防止慢站耗尽全局并发。
- 将异步视频或大文件媒体做成带幂等键的任务服务；任务创建和查询不应在浏览器或文本流中无限等待。

## 6. 可观测性与审计

网关记录请求标识、AI OPS、结果状态、耗时和用量；管理端可以据此追查请求是否发生回退。普通日志和员工界面不得显示完整 Key、上游 API Key、完整中转站认证头或原始上游错误体。

对话记录与路由选择分离：换站、失败回退或 Key 轮换不能清空客户端本地的会话历史；平台审计只记录必要的调用元数据，不以“找最快”为理由复制用户输入到多个上游。
