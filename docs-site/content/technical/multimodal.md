# 图片、视频与异步任务

## 1. 当前接口与后续任务服务

员工使用同一 Key 调用文本、图片、视频和音频，但每个模态必须使用适合自身的协议和调度模型。当前已交付的是统一 JSON 网关：`/v1/images/generations`、`/v1/videos` 和 `/v1/audio/speech` 使用 `ai-ops`，先从对应模态的内部候选组并发健康探测并选定站点，再原样转发。文本 Chat/Responses 只选择文本候选，媒体模型不会误入文本请求。

当前网关不会为媒体创建自己的 job、上传资产或替中转站轮询任务。下文的状态机、对象存储和队列是后续“媒体作业服务”的实施规范；在该服务落地前，不得将这些能力展示成已经存在的 UI 或 API。

| 模态 | 典型执行方式 | 返回方式 | 路由首要指标 |
| --- | --- | --- | --- |
| 文本、代码 | 同步、流式 | SSE 片段 | TTFT、错误率、并发 |
| 图片 | 当前 JSON 转发；后续短任务或异步 | 当前保留上游响应；后续图片结果或平台 job_id | 队列、成功率、规格支持 |
| 视频 | 当前 JSON 转发；后续长任务、异步 | 当前保留上游响应；后续立即返回平台 job_id | 预计排队、时长、规格、成本 |
| 音频 | 当前 JSON 转发；后续同步或异步 | 当前保留上游响应；后续音频、文本或平台 job_id | 时长、队列、文件限制 |

不要为了表面“OpenAI 兼容”而把视频伪装成无限等待的聊天请求。对于视频，用户体验的关键是快速确认、可靠状态和可恢复下载。

## 2. 后续媒体作业状态机

~~~mermaid
stateDiagram-v2
  [*] --> queued
  queued --> dispatching
  dispatching --> running
  dispatching --> failed
  running --> succeeded
  running --> failed
  queued --> cancelled
  dispatching --> cancelled
  running --> cancelling
  cancelling --> cancelled
  succeeded --> expired
  failed --> [*]
  cancelled --> [*]
  expired --> [*]
~~~

状态含义：

- queued：已通过校验和额度预占，等待工作进程。
- dispatching：正在选择路由并向中转站提交。
- running：上游已接受或正在生成。
- succeeded：结果已验收、入对象存储并可授权下载。
- failed：不可恢复失败；必须归一化错误原因并释放未消费额度。
- cancelled：员工或管理员取消成功，或上游确认停止。
- expired：到达组织设定的资产保留期，结果不再可访问。

## 3. 输入与输出资产

上传文件不应由应用服务器全量转发。推荐流程：

1. 员工请求上传许可。
2. 服务端校验文件类型、大小、员工权限和计划用途。
3. 返回短时对象存储上传地址。
4. 浏览器或客户端直接上传。
5. 作业创建时引用受控 asset_id。
6. 工作进程为上游生成临时读取地址或受控上传流。
7. 结果保存为独立 output_asset，并通过短时签名 URL 下载。

必须进行文件类型检测、病毒/恶意内容扫描、大小限制和所有权校验。任何员工都不能通过 asset_id 读取其他员工的输入或结果。

## 4. 图片任务

图片生成和编辑要求目录记录模型支持的尺寸、宽高比、参考图数量、输出格式、质量档位和编辑能力。

若上游通常在短时间内完成，网关可选择在一个有限等待窗口内返回结果；超过窗口后自动转换为标准 job。无论哪种情况，API 都应能返回可查询的任务身份，避免客户端遇到网络中断后无法判断图片是否已生成。

## 5. 视频任务

视频作业默认异步。提交接口只做参数验证、预算预占、任务创建和排队；不得等待中转站完成。

视频路由除成功率外还要考虑：

- 请求的时长、分辨率、帧率、首尾帧或音频条件是否被模型支持。
- 当前中转站的排队长度和基于历史任务计算的预计完成时间。
- 单任务和每日预算是否足够。
- 上游是否支持回调、查询、取消、失败重试和下载有效期。

优先使用上游 webhook。无法回调时，任务工作进程采用退避轮询：开始阶段较密集，任务运行稳定后逐渐降低频率，完成临近时按上游建议调整。绝不能让每个员工浏览器各自轮询中转站。

## 6. 音频任务

音频统一目录应区分语音生成、语音识别、音频理解和音乐或声音生成等能力。大文件转写需要异步队列；小型语音生成可同步返回或走短作业。

系统记录时长、采样率、语言、输入输出格式和是否允许流式。音频文件同样按员工和作业隔离，下载使用短时授权。

## 7. 队列、并发与预算

文本、图片、视频和音频必须使用独立工作队列与并发池：

~~~text
文本实时池      高优先级、无长队列
图片任务池      中等并发、短时任务
视频任务池      严格并发、成本预占、预计等待
音频任务池      按文件时长和模型能力分流
~~~

视频任务提交时预占额度；成功后按实际消耗结算，失败或取消时释放未消耗部分。图片和音频同样支持估算与实际差异调整。预算记录必须幂等，重复回调不能重复扣费或退款。

## 8. 可靠性

- 每个创建作业请求都要求 Idempotency-Key。
- 平台生成 job_id，与上游 job_id 分离保存。
- 工作进程可以安全重启并从状态恢复。
- 上游状态不明时进入 reconciliation，而不是立即判定失败并重复提交。
- 取消是尽力操作；若上游无法取消，状态需明确说明仍可能产生费用。
- 结果下载失败不等于上游生成失败，资产交付要可重试。

## 9. 员工可见反馈

员工应当看到可操作的状态，而不是模糊加载图标：

| 状态 | 员工文案示例 |
| --- | --- |
| queued | 已进入队列，正在等待可用生成资源 |
| running | 正在生成，可离开页面后稍后返回查看 |
| succeeded | 已完成，可预览、下载或继续编辑 |
| failed | 生成未完成，显示安全的失败原因和重试建议 |
| cancelled | 已请求取消，未消费额度将自动核算 |

上游名称、原始错误体、认证信息和内部路由不会展示给员工。
