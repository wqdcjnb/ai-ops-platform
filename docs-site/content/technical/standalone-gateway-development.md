# 独立 AI 网关开发文档与分步完成表

::: info 文档目标
本文用于把 AI OPS 从“管理控制台 + 模拟/只读数据”逐步建设为可独立承载 WorkBuddy、Codex Desktop 及其他兼容客户端请求的 AI 网关。开发必须严格按阶段推进：完成当前阶段的代码、测试、文档和验收后，才能进入下一阶段；每个阶段结束后向项目负责人汇报，等待确认再继续。
:::

## 1. 目标与边界

> 当前进度：**P00 至 P08 已完成**。当前已支持 OpenAI 兼容上游的模型列表、非流式聊天、SSE 流式聊天、最小 Responses 兼容层，以及数据库 Key、单模型绑定、基础备用路由、连接器隔离和本地用量/告警/审计闭环。

### 1.1 最终目标

员工只需要把 WorkBuddy、Codex Desktop 或其他兼容客户端指向 AI OPS，管理员在 AI OPS 中完成人员、Key、模型、额度、告警和审计管理；New API 和 CPA 只作为可选上游连接器，不再是平台运行的必需管理入口。

```text
WorkBuddy / Codex Desktop / 其他客户端
          |
          v
AI OPS Gateway（数据面）
          |
          +-- OpenAI 兼容接口
          +-- Ollama / 本地模型
          +-- 可选 New API
          +-- 可选 CPA

AI OPS BFF + SQLite（控制面）
          |
          +-- 人员、Key、路由、额度、用量、告警、审计
```

### 1.2 必须区分的两种需求

| 需求 | 是否需要 New API/CPA | 实现方式 |
| --- | --- | --- |
| 不打开 New API/CPA 管理网页 | 可继续运行 | AI OPS BFF 通过服务端适配器读取或管理上游 |
| 不启动 New API/CPA 进程 | 不需要 | AI OPS Gateway 直接连接 OpenAI 兼容服务或 Ollama |
| 没有任何模型服务仍要进行真实对话 | 不可行 | 必须存在一个真实推理服务；否则只能使用模拟模式 |

当前 BFF 是控制面，网关已经提供 `/v1/models`、`/v1/chat/completions`、SSE 流式聊天和最小 `/v1/responses`；数据库 Key 校验、每个 Key 的单模型绑定和停用/过期校验已完成。WorkBuddy 和 Codex Desktop 仍应在真实上游和客户端实机验收完成后再切换正式地址。

### 1.3 客户端接入原则

| 客户端 | 第一版目标 | 必须验证的内容 |
| --- | --- | --- |
| WorkBuddy | 自定义 Base URL、Key 和模型后完成普通/流式对话 | Chat Completions、SSE、取消、工具调用行为 |
| Codex Desktop | 通过企业/自定义兼容入口连接 AI OPS | Responses、SSE、工具调用、鉴权方式和自定义地址能力 |
| 其他 OpenAI 兼容客户端 | 作为兼容性扩展 | `/v1/models`、`/v1/chat/completions` 和错误格式 |

Codex Desktop 是否允许直接配置自定义网关地址、使用哪种协议和需要哪些 Header，必须在 P03 用当前安装版本实机记录确认；不能因为 WorkBuddy 可配置，就假设 Codex Desktop 的配置方式完全相同。如果客户端不提供自定义入口，则需要为该客户端增加本机代理或采用其官方支持的兼容配置。

## 2. 开发纪律

1. 一次只推进一个阶段。
2. 每个阶段必须同时完成代码、测试、文档和验收记录。
3. 阶段验收不通过时只修复当前阶段，不跨阶段堆功能。
4. 所有凭据只放服务端环境变量或本地密钥存储，不进入浏览器、Git、日志和导出文件。
5. 真实上游接入和本地模拟数据必须明确标记，模拟成功不能冒充真实链路成功。
6. 每个阶段结束后向负责人汇报：完成内容、测试证据、已知问题、下一阶段和是否需要确认。

## 3. 分阶段开发顺序

### 第 0 步：冻结网关范围与运行模式

**目标**：确认第一版只做可运行的独立网关，不同时实现所有供应商特性。

**工作项**

- 增加 `gatewayMode`：`standalone`、`new_api`、`cpa`。
- 确定默认模式为 `standalone`。
- 确定首个上游：OpenAI 兼容接口或 Ollama，二选一即可开工。
- 确定网关端口、客户端 Key 格式、模型别名规则和日志留存范围。
- 明确第一版不承诺图片、MCP、复杂工具编排等扩展能力。

**退出条件**

- `standalone` 模式和首个上游已书面确定。
- 没有真实凭据写入仓库。
- 已建立网关配置模板和本地启动说明。

**汇报内容**：运行模式、首个上游、接口范围、未纳入范围。

### 第 1 步：建立独立网关骨架

**目标**：在现有 Fastify 服务中建立数据面模块，但暂不接真实模型。

**工作项**

- 新建 `apps/server/src/gateway/` 模块。
- 增加网关配置加载和启动校验。
- 增加以下健康检查接口：

```text
GET /gateway/health
GET /gateway/config
```

- `config` 只返回模式、上游名称和能力，不返回任何密钥。
- 增加统一 `requestId`、结构化日志和错误响应格式。
- 增加网关路由与现有管理 API 的隔离测试。

**验收**

- 服务可在没有 New API/CPA 的情况下启动。
- 错误配置会在启动时明确报错。
- 健康检查不会泄露密钥或完整环境变量。

### 第 2 步：接入首个 OpenAI 兼容上游

**目标**：实现最小非流式真实请求。

**工作项**

- 新增上游适配器接口：`listModels`、`chatCompletion`、`cancel`。
- 实现 OpenAI 兼容适配器；上游地址和密钥仅由服务端读取。
- 增加 `GET /v1/models`。
- 增加 `POST /v1/chat/completions`。
- 将上游错误转换为统一错误码，不返回内部 URL、密钥或堆栈。
- 增加模型别名到实际模型的映射。

**验收**

- 使用 AI OPS Key 可以完成一次真实非流式对话。
- 无效 Key、未授权模型、上游超时和 429/5xx 都有稳定响应。
- 日志可以用 `requestId` 定位请求，但不保存完整提示词和回答。

### 第 3 步：实现流式响应与客户端兼容

**目标**：让 WorkBuddy 和 Codex Desktop 能通过 AI OPS 完成基础对话。

**工作项**

- 支持 SSE 流式输出。
- 透传或转换 `usage`、完成原因和模型字段。
- 处理客户端断开、上游取消和超时。
- 增加 `POST /v1/responses` 的最小兼容层；不支持的字段明确返回“不支持”。
- 编写 WorkBuddy 和 Codex Desktop 本地接入说明，但在验收前不修改用户配置。

**验收**

- WorkBuddy 使用 AI OPS 地址完成普通对话和流式对话。
- Codex Desktop 完成当前版本支持范围内的普通/流式调用；若不支持自定义入口，记录代理或配置替代方案。
- 客户端取消不会导致服务端连接泄漏。
- 发生上游异常时客户端能看到可理解的错误。

### 第 4 步：接入 AI OPS Key、单模型绑定和路由策略

**目标**：把网关请求纳入现有本地 SQLite 控制面。

**工作项**

- 为客户端 Key 增加创建、掩码、停用、轮换和过期状态。
- 每个 Key 关联人员、用途和一个绑定模型；模型从全局业务模型目录选择，需要多个模型时为同一人员分别创建多个 Key，人员档案不维护模型白名单。
- 增加路由策略：默认模型、备用模型、是否允许降级。
- 请求进入上游前完成权限检查。
- 所有 Key 操作和路由变更写入审计日志。

**验收**

- 停用 Key 立即无法调用。
- 未授权模型在到达上游前被拒绝。
- 页面、日志、导出和错误中均不出现完整 Key。

### 第 5 步：用量、审计和告警闭环

**目标**：让控制台展示网关产生的真实本地数据。

**工作项**

- 记录请求数、输入/输出 Token、耗时、状态、模型和人员归属。
- 记录网关请求与管理操作的审计事件。
- 在用量、告警、审计页面接入网关数据源。
- 增加本地导出，并对 Key、Token 和敏感字段脱敏。

**验收**

- 一次 WorkBuddy 调用可以在用量、告警和审计页面关联查询。
- 失败、取消、重试不会重复计量。
- 导出文件不包含完整凭据和原始对话正文。

### 第 6 步：可选 New API/CPA 连接器

**目标**：在独立模式稳定后，才增加可选上游，不改变默认运行方式。

**工作项**

- 将 New API 和 CPA 封装为与 OpenAI 兼容适配器相同的接口。
- 在上游账号页面显示连接状态、能力和最近检查时间。
- 每条路由明确标记 `standalone`、`new_api` 或 `cpa`。
- 禁止正式路由无提示地回退到 CPA 实验账号。

**验收**

- 停止 New API/CPA 后，`standalone` 路由仍可用。
- 连接器不可用时只影响绑定它的路由。
- 管理员无需打开上游管理网页即可查看状态。

### 第 7 步：自动化验收与故障测试

**目标**：验证核心链路可以长期运行。

**必须覆盖**

- 添加人员、批量导入。
- 创建、停用和轮换 Key。
- Key 的单模型绑定与模型权限拒绝。
- 用量和审计回溯。
- 告警处置。
- 审计回溯。
- WorkBuddy 和 Codex Desktop 的非流式、流式、取消、错误 Key 和错误模型。
- 上游超时、429、5xx、断开和服务重启。

**退出条件**

- 关键浏览器流程、网关集成测试和静态检查通过。
- 至少完成一次从启动到调用、查询用量、查看审计的完整演示。
- 已知问题有影响范围和下一步处理计划。

### 第 8 步：内部测试发布

**目标**：允许少量内部人员使用独立网关模式。

**发布规则**

- 不启用已废弃的软额度链路，也不在网关请求中生成额度告警。
- 控制台本地环境通过 `AI_OPS_SOFT_QUOTA_ENABLED=false` 隐藏软目标、临时额度和软额度告警；关闭后相关写接口返回 `SOFT_QUOTA_DEPRECATED`，硬限流不因本开关自动开启。
- 使用独立测试 Key 和测试模型别名。
- 每日备份 SQLite 和配置模板。
- 任何真实生产 Key、个人 OAuth 或客户数据都不能直接导入。
- 每周复盘成功率、延迟、错误、用量和费用估算。

## 9. P03 阶段完成记录

本阶段补齐流式客户端兼容，但仍不把数据库 Key 和用量写入混入数据面。

### 已完成

1. `POST /v1/chat/completions` 支持非流式和 SSE 流式两种模式。
2. 上游 SSE 数据会逐块透传，并在结束时发送 `data: [DONE]`。
3. 客户端断开会中止上游 `AbortController`，并通过请求 ID 取消活动流；超时和上游异常会转换为 SSE `error` 事件。
4. 增加最小 `POST /v1/responses` 兼容层：支持文本/消息输入和非流式输出；未支持字段及 Responses 流式输出会明确返回 `GATEWAY_UNSUPPORTED`。
5. 新增 SSE 解析、流式路由、客户端凭据、取消和 Responses 转换测试。
