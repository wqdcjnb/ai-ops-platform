# 运行手册

## 1. 日常运行目标

当前运行团队的首要任务是保持AI OPS目录可信、文本路径低延迟、JSON 多模态转发可用、凭据安全和预算可控。管理员不需要逐个登录中转站处理员工请求。

当前版本没有平台自建媒体队列、对象存储、跨设备会话同步或独立 worker。本文关于队列、回调、资产、设备和跨设备恢复的条目是这些能力上线后的运行要求，不能当作当前已启用的控制台功能。

## 2. 每日检查

| 检查项 | 关注内容 | 异常处理 |
| --- | --- | --- |
| 中转站健康 | 认证、成功率、TTFT、429、熔断 | 降权、暂停路由或重新验证 |
| 目录同步 | 最后成功时间、模型变化、适配失败 | 保留旧快照，检查适配器并人工确认发布 |
| 文本路径 | p50/p95 TTFT、在途数、流式中断 | 检查候选路由、连接池和区域网络 |
| 媒体队列 | 图片/视频/音频排队、失败、回调积压 | 扩容专属 worker、暂停高成本提交或修复上游 |
| 预算 | 组织总额、视频预占、异常增长 | 降低并发、告警管理员、必要时暂停模型 |
| 安全 | 失败登录、Key 异常、设备变化、下载异常 | 撤销受影响 Key 或设备并调查 |

## 3. 中转站故障处理

1. 确认故障精确到中转站、模型和模态，而非仅查看总状态。
2. 检查是否已经自动熔断；若未熔断且证据充分，人工禁用相关路由。
3. 确认同模型备用路由能处理新请求。
4. 对在途文本请求记录中断原因；不要从头自动重发已输出内容。
5. 对媒体作业进入 reconciliation，先查询上游实际状态再决定重试或退款。
6. 修复后以少量 half_open 探测流量验证，再逐渐恢复权重。

## 4. 高延迟处理

当 TTFT 或媒体排队异常时，按以下顺序排查：

1. 查看模型级健康快照、在途请求、队列长度和 429。
2. 判断是单一中转站、区域网络、连接池、网关、Redis 还是客户端问题。
3. 确认热路径是否错误地触发了同步目录、同步日志写入或全站探测。
4. 临时降低慢路由权重，确保至少保留一个健康备选。
5. 如需扩容，只扩容受影响的文本或媒体池，不盲目扩大全部服务。
6. 记录恢复前后 TTFT、成功率和请求量，防止反复切换造成抖动。

## 5. 媒体作业处理

| 场景 | 操作 |
| --- | --- |
| 长时间 queued | 检查对应模态 worker、预算预占、模型并发和队列优先级 |
| 上游已完成但平台未完成 | 查询上游 job，重试资产收集和存储，不重复提交生成 |
| 回调重复 | 使用平台 job 与上游 job 的幂等约束，重复事件只更新时间戳 |
| 员工请求取消 | 发送取消并提示尽力执行；按上游最终状态结算 |
| 结果下载失败 | 检查对象存储、CDN、短时签名和员工资产权限 |
| 视频成本异常 | 立即暂停受影响模型或规格，核对预占和实际结算 |

## 6. 凭据或 Key 风险处理

员工 Key 疑似泄露：

1. 立即撤销 Key 或禁用员工。
2. 检查相关 request_id、来源、模型、预算和资产访问。
3. 为员工创建新 Key 或要求重新登录。
4. 撤销可疑设备令牌并要求重新连接。

中转站凭据疑似泄露：

1. 立即将站点所有路由设为 disabled 或 open。
2. 在上游轮换凭据并在密钥管理系统更新引用。
3. 使用最小探测验证新凭据，不在聊天、工单或日志中粘贴明文。
4. 恢复路由前审查近期费用和异常请求。

## 7. 发布与回滚

每次发布前：

- 执行类型检查、单元测试、集成测试和目标模态回归。
- 验证目录快照、路由配置和数据迁移可回退。
- 对连接器版本做兼容矩阵测试。
- 在灰度环境真实调用文本、图片和视频路径。

回滚时：

- 优先回滚应用版本或路由策略，不回滚已产生的作业事实。
- 使用目录快照恢复已验证模型集合。
- 保留 request_id、job_id 和预算数据；审计数据遵循最多 30 天的保留策略。
- 必要时暂停高成本媒体入口，直到状态一致性恢复。

## 8. 定期维护

- 每周审查中转站健康、成本、未使用模型和连接器版本。
- 每月演练 Key 撤销、站点熔断、队列重启和对象存储恢复。
- 定期删除到期资产、过期设备授权和超出保留期的审计数据。
- 在中转站协议或客户端版本升级前，于隔离环境重新验证适配器与连接器。
