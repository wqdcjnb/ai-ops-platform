# 最终决策

## D-001：不管理个人客户端账号

**决定**：平台管理多个已授权中转站，不管理、共享、分配或轮换个人客户端账号。

**原因**：产品的核心是稳定的统一模型服务、可控路由和员工体验，而不是账号资源管理。

## D-002：员工使用唯一全能力 Key

**决定**：每名员工默认只有一把有效 Key，且只调用唯一员工可见模型AI OPS。

**原因**：员工不应为文本、图片、视频或不同中转站管理多把 Key。AI OPS在后台混合使用原始模型，成本、并发和可见性由平台统一治理。

## D-003：AI OPS不等于单一原始模型

**决定**：对外只公开 API ID 为 ai-ops、显示名为“AI OPS”的虚拟模型；多个中转站和原始模型仅作为内部路由候选。

**原因**：员工体验需要一个稳定模型名，平台仍需要按文本、代码、图片、视频、音频、速度、质量和容量混合使用上游能力。

## D-004：统一 Key 不等于统一执行协议

**决定**：文本、图片、视频和音频使用正确的端点与任务模型。

**原因**：视频和大媒体任务需要异步作业，不能为表面统一而牺牲可靠性和等待时间。

## D-005：数据面以统一网关为唯一入口

**决定**：员工客户端只访问 AI OPS 网关，不直接访问任何中转站。

**原因**：路由、熔断、计量、预算、审计和凭据隔离必须在统一位置执行。

## D-006：Codex 与 WorkBuddy 都使用本地连接器

**决定**：本机 AI OPS 连接器直接更新用户级 `~/.codex/config.toml`、`AI_OPS_TOKEN` 用户环境变量和 `~/.workbuddy/models.json` 中的 AI OPS 条目；员工不再下载 TOML 或 JSON。

**原因**：浏览器不能安全地直接修改本机应用配置。回环连接器提供可验证的本地写入路径，并限制页面来源、原子写入和保留其他模型；它不读取 Codex `auth.json`，不触碰 Codex/WorkBuddy 对话数据库。

## D-007：导入配置不得破坏客户端会话

**决定**：导入配置只新增 AI OPS Provider，不删除或重置 Codex / WorkBuddy 的既有配置和会话；网关路由、Key 轮换和回退也不得主动清除客户端历史。

**原因**：当前系统有调用与对话审计，但这不等于完整跨设备会话备份。跨设备恢复应在未来以稳定会话 ID、turn 持久化和客户端同步协议单独验收。

## D-008：Codex Provider 不依赖 OpenAI 账号

**决定**：ai-ops 自定义 Provider 使用 AI OPS 平台 Key；连接器只检测 Codex 登录状态，不创建、伪造或接管 OpenAI/ChatGPT 身份。已登录或未登录的员工都能按自定义 Provider 配置 AI OPS。

**原因**：AI OPS 提供的是独立授权的模型服务。强制员工拥有或登录上游账号会破坏统一 Key 体验。

## D-009：并发探测，单站真实执行

**决定**：网关对健康过期候选并发探测 `/models`，首个成功者获胜并取消其他探测；文本、图片、视频和语音的真实请求只发往一个胜出站点。

**原因**：用户感知的等待时间来自尽快取得一个健康路径；重复真实请求会造成对话重复、图片/视频重复生成和重复计费，不能用作竞速手段。

## D-010：旧文档和旧实现不构成验收

**决定**：任何早于本方案的控制面、凭据模式、单模型 Key 和仅管理员模式文档均已废弃。

**原因**：它们与最终产品边界冲突。旧代码仅能作为迁移参考，不能被当作新功能已完成的证据。
